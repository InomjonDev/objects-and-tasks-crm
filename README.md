# Мини-CRM «Объекты и задачи»

Тестовое приложение для строительной компании: постановщики управляют объектами и задачами, исполнители выполняют назначенную работу и отправляют её на проверку.

Приложение: [objects-and-tasks-crm-one.vercel.app](https://objects-and-tasks-crm-one.vercel.app). Репозиторий: [InomjonDev/objects-and-tasks-crm](https://github.com/InomjonDev/objects-and-tasks-crm).

**Стек:** React, TypeScript, Vite, React Router, shadcn/ui (preset `b2fC`, pointer), Tailwind, Supabase Auth/Postgres, Vercel. Внешний сервер приложения не нужен: правила доступа и изменения данных выполняются в Postgres.

## Запуск

Нужны Node.js 24 и Yarn 4.9.2. Если системная команда `yarn` запускает Yarn 1, используйте `corepack yarn`.

```sh
corepack yarn install --immutable
cp .env.example .env.local
# Заполните URL и publishable key проекта Supabase.
corepack yarn dev
```

Переменные фронтенда: `VITE_SUPABASE_URL`, `VITE_SUPABASE_PUBLISHABLE_KEY`. Publishable key рассчитан на использование в браузере; доступ к строкам ограничивают RLS и права базы. Секретные/service-role ключи запрещено помещать в `VITE_*`, репозиторий или настройки сборки фронтенда.

## Настройка базы

Используйте отдельный Supabase Free проект. Миграции лежат в `supabase/migrations` и применяются по порядку. Через Supabase CLI 3:

```sh
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push --remote --skip-vault --yes
```

Перед применением проверьте `supabase db push --help` в установленной версии CLI. Альтернатива — выполнить SQL миграции в SQL Editor нового пустого проекта; это не записывает историю миграций CLI автоматически.

В Dashboard → Authentication отключите **Allow new users to sign up**. Локальная конфигурация также запрещает регистрацию. Настройте Site URL на адрес приложения. Не включайте схему `private` в список exposed schemas Data API.

Для локальной разработки можно использовать `supabase start` с Docker. CLI 3 также поддерживает экспериментальную команду `supabase stack start --runtime native`; она не нужна для облачного запуска. Проверка SQL ниже не требует Docker.

## Тестовые пользователи и данные

Скопируйте `.env.admin.example` в `.env.admin` и заполните URL, publishable key и административный ключ **только локально**. Указанный проект должен быть отдельной тестовой базой с применёнными миграциями.

```sh
corepack yarn seed:demo
```

Скрипт создаёт одного постановщика, двух исполнителей, три объекта и восемь задач. Статусы формируются через разрешённые действия реальных пользователей. Пароли случайные; email подтверждаются административно, письма не отправляются. Доступы записываются в игнорируемый файл `.local/demo-accounts.json` с правами `0600`. Передавайте их проверяющему лично, не добавляйте в README или Git.

Роли находятся в `profiles`, а не в редактируемых пользователем метаданных авторизации. Пользователь меняет своё имя через защищённый RPC, без возможности изменить роль. Постановщики создают сотрудников на странице профиля через серверную Edge Function. Повторное назначение роли через Dashboard выполняйте осознанно: это административное действие, отсутствующее в интерфейсе CRM.

## Проверки

```sh
corepack yarn test
corepack yarn test:db
corepack yarn test:api
corepack yarn test:staff
corepack yarn typecheck
corepack yarn lint
corepack yarn build
```

- `test`: соответствие доступных кнопок циклу статусов.
- `test:db`: реальная миграция в временном PostgreSQL, 100 комбинаций ролей и переходов, RLS, права API, валидация, история, переназначение и удаление. Нужны локальные `initdb`, `pg_ctl`, `psql`; можно задать `PG_BIN`. Временная база удаляется после проверки.
- `test:api`: прямые запросы в Supabase с тремя демо-аккаунтами из `.local/demo-accounts.json`. Нужна `.env.admin`; административный ключ дополнительно позволяет проверить физическое сохранение истории. Тест создаёт отдельные записи и мягко удаляет их, не меняя демо-задачи. Удалённые тестовые строки сохраняются в базе по правилам приложения.

Ручной сценарий: создать объект и задачу → исполнитель берёт в работу → отправляет на проверку → постановщик возвращает с комментарием → исполнитель повторно выполняет → постановщик принимает. Проверить вход второго исполнителя, недоступность чужой задачи по прямой ссылке, редактирование, переназначение, удаление, выход и обновление страницы по вложенному URL.

## Профиль и сотрудники

На странице `/profile` есть имя, email, роль, дата регистрации, сводка задач, выбор языка и быстрые действия. Имя можно редактировать; email и роль доступны только для чтения. Постановщикам дополнительно доступен список сотрудников и создание аккаунтов обеих ролей. Email сотрудников выдаётся только через RPC `list_staff`, который проверяет роль постановщика.

Перед использованием создания сотрудников разверните функцию после применения миграций:

```sh
supabase functions deploy create-staff --remote=YOUR_PROJECT_REF --use-api --yes
```

Функция использует встроенные серверные `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. Дополнительные секреты фронтенду и Vercel не нужны. Проверка JWT шлюзом отключена в конфигурации этой функции: сама функция проверяет bearer-токен через `auth.getUser()` и заново читает роль из базы на каждом запросе. Анонимный запрос получает 401, исполнитель — 403. Триггер создаёт профиль при назначении администратором защищённых `app_metadata`; редактируемые `user_metadata` в назначении ролей не участвуют. При последующих обновлениях метаданных существующие имя и роль не перезаписываются.

Пароль для первого входа задаёт постановщик; письма не отправляются, доступы передаются лично. Автоматическое истечение пароля, смена email/роли и удаление сотрудников в интерфейсе не добавлялись. `test:staff` проверяет создание обеих ролей, вход новых сотрудников, изоляцию списка, редактирование собственного имени, запрет повышения роли и ошибки ввода. Тест удаляет только созданные им аккаунты, не меняя существующие учётные записи.

Русский и English доступны на входе, в шапке и профиле. Выбор сохраняется в браузере; пользовательские названия, адреса и комментарии не переводятся. Скелетоны используют shimmer-анимацию и учитывают reduced motion.

## Развёртывание

Импортируйте GitHub-репозиторий в Vercel Free. Укажите две публичные переменные фронтенда и `ENABLE_EXPERIMENTAL_COREPACK=1` для Yarn 4, используйте Vite preset, команду `yarn build`, каталог `dist`. `vercel.json` содержит перенаправление маршрутов SPA на `index.html`. Административные переменные Vercel не нужны.

После развёртывания войдите каждым демо-пользователем, пройдите цикл задачи и обновите страницы `/projects/:id` и `/tasks/:id` напрямую.

## Устройство и решения

- `src`: авторизация, общий снимок доступных данных, страницы, формы, правила показа действий и компоненты preset.
- `supabase/migrations`: таблицы, RLS и транзакционные функции изменения данных.
- `scripts`: подготовка демо-данных и проверки базы/API.
- `docs`: объяснение для руководителя, допущения и сообщение для hh.ru.

Клиент читает данные с RLS. Запись разрешена только через ограниченные RPC-обёртки; привилегированные реализации находятся в `private`, проверяют `auth.uid()` и роль, используют фиксированный `search_path`. Смена статуса блокирует строку и записывает историю в той же транзакции. Прямые изменения таблиц и истории запрещены для обычных пользователей.

Схема типов находится в `src/database.types.ts`; при изменении миграций синхронизируйте её с базой (`supabase gen types typescript`). Ограничения и принятые решения перечислены в `docs/decisions.md`.

Конфиги используют расширения `.mjs`/`.mts`, а `src/package.json` явно задаёт ES-модули для исходников. Это позволяет Yarn 4 работать в среде Vercel без конфликта корневого `type: module`.
