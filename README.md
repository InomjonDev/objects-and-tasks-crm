# Мини-CRM «Объекты и задачи»

Тестовое задание для строительной компании. Постановщик назначает задачи по объектам, исполнитель выполняет работу и отправляет результат на проверку.

- **Работающее приложение:** [objects-and-tasks-crm-one.vercel.app](https://objects-and-tasks-crm-one.vercel.app).
- **Репозиторий:** [InomjonDev/objects-and-tasks-crm](https://github.com/InomjonDev/objects-and-tasks-crm).
- **Объяснение для руководителя без технических терминов:** [как работает система и защищены данные](docs/manager-explanation.md).
- **Решения, допущения и ограничения:** [список принятых решений](docs/decisions.md).
- **Результаты проверок:** [проверка приложения, базы и прямых запросов](docs/verification.md).

Демо-доступы одного постановщика и двух исполнителей передаются в том же сообщении на hh.ru, что и ссылка на приложение. Пароли и административные ключи в открытом репозитории не публикуются. Исходный демонстрационный набор содержит три объекта и восемь задач во всех пяти статусах.

## Соответствие техническому заданию

| Требование | Реализация |
| --- | --- |
| React + TypeScript и Supabase | React, TypeScript, Vite, Supabase Auth и PostgreSQL; интерфейс на shadcn/ui |
| Две роли, несколько пользователей каждой роли | Постановщики видят все активные объекты и задачи; исполнители — только назначенные им задачи и связанные объекты |
| Управление объектами | Создание, редактирование и удаление; поля «Название» и «Адрес»; задачи со статусами в карточке объекта |
| Управление задачами | Название, описание, объект, исполнитель, статус, автор и дата создания; создание, редактирование, назначение и удаление постановщиком |
| Предусмотренные статусы и переходы | Все шесть переходов из задания; остальные запрещены в базе |
| Возврат на доработку | Требуется непустой комментарий; проверка действует и при прямом запросе |
| История изменений | Кто, когда, из какого статуса в какой и комментарий; история доступна обеим ролям в пределах доступа к задаче |
| Пять обязательных экранов | Вход, список объектов, карточка объекта, карточка задачи, «Мои задачи» исполнителя |
| Только доступные действия в интерфейсе | Кнопки зависят от роли, назначения и текущего статуса задачи |
| Защита при обращении в обход интерфейса | Ограничения чтения в базе, проверка операций и переходов на сервере, запрет прямой записи истории |
| Материалы для сдачи | Работающее приложение, репозиторий с миграциями, это руководство, объяснение для руководителя и список допущений |

### Цикл задачи

| Из статуса | В статус | Кто выполняет | Условие |
| --- | --- | --- | --- |
| Создание | Новая | Постановщик | Начальный статус задаёт база |
| Новая | В работе | Назначенный исполнитель | — |
| В работе | На проверке | Назначенный исполнитель | — |
| На проверке | Принята | Постановщик | — |
| На проверке | На доработке | Постановщик | Комментарий обязателен |
| На доработке | В работе | Назначенный исполнитель | — |

Постановщик не может самостоятельно взять задачу в работу или отправить её на проверку. Исполнитель не может принять свою работу, назначить другого исполнителя или изменить данные задачи.

## Как проверить приложение

1. Войти постановщиком, открыть объект и создать задачу с назначенным исполнителем.
2. В другом браузере или приватном окне войти этим исполнителем: задача должна быть доступна, чужие задачи — скрыты, в том числе по прямой ссылке.
3. Взять задачу в работу и отправить на проверку.
4. Постановщиком вернуть задачу на доработку. Без комментария действие не выполняется.
5. Исполнителем снова взять задачу в работу и отправить на проверку; постановщиком принять результат.
6. Открыть историю и проверить участников, даты, переходы и комментарий.

## Защита данных

- **Ограничения на уровне строк (RLS)** включены на всех четырёх таблицах приложения. База проверяет, какие записи разрешено читать текущему пользователю. Скрытие кнопок не является единственной защитой.
- Исполнитель видит только свои задачи и объекты с такими задачами. На общем объекте задачи других исполнителей ему не выдаются.
- Изменения объектов, задач и собственного имени выполняются через ограниченные функции базы — RPC. Привилегированные реализации находятся в закрытой схеме `private`, проверяют пользователя и права, используют фиксированный путь поиска SQL-объектов.
- При смене статуса база блокирует запись, проверяет допустимость перехода и сохраняет статус с историей в одной транзакции. Автор изменения и время определяются сервером. Повторный запрос со старым статусом отклоняется.
- Постановщики и исполнители не могут напрямую вставить, исправить или удалить историю через API. История формируется функциями базы.
- Открытая регистрация отключена. В браузере используется только публичный ключ Supabase; административный ключ используется исключительно локальными служебными скриптами и серверной функцией создания сотрудников.

## Локальный запуск

Нужны Node.js 24, Yarn 4.9.2 и подготовленный проект Supabase. Если системная команда `yarn` запускает Yarn 1, используйте `corepack yarn`.

```sh
git clone https://github.com/InomjonDev/objects-and-tasks-crm.git
cd objects-and-tasks-crm
corepack yarn install --immutable
cp .env.example .env.local
# Заполните .env.local параметрами своего проекта Supabase.
corepack yarn dev
```

Приложение откроется по адресу, который выведет Vite, обычно `http://localhost:5173`.

| Переменная фронтенда | Значение |
| --- | --- |
| `VITE_SUPABASE_URL` | URL проекта Supabase |
| `VITE_SUPABASE_PUBLISHABLE_KEY` | Публичный ключ проекта |

Ключ `service_role` и другие секретные ключи нельзя помещать в переменные `VITE_*`, репозиторий или окружение сборки фронтенда.

### Подготовка новой базы

Используйте отдельный проект Supabase Free и Supabase CLI 3. Все изменения схемы, права, проверки и триггеры находятся в [supabase/migrations](supabase/migrations).

```sh
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase db push --remote --skip-vault --yes
supabase functions deploy create-staff --remote=YOUR_PROJECT_REF --use-api --yes
```

В панели Supabase → Authentication отключите **Allow new users to sign up** и задайте адрес приложения в **Site URL**. Не добавляйте схему `private` в список схем, доступных через API. Локальная конфигурация также запрещает регистрацию.

### Демо-пользователи и данные

Скопируйте `.env.admin.example` в `.env.admin`. Заполните URL, публичный и административный ключи **только локально** и выполните:

```sh
corepack yarn seed:demo
```

Скрипт создаёт одного постановщика, двух исполнителей, три объекта и восемь задач. Разные статусы формируются через разрешённые действия пользователей. Случайные пароли записываются в игнорируемый файл `.local/demo-accounts.json` с правами `0600`. Письма не отправляются. Эти доступы нужно передать проверяющему лично.

## Дополнения к исходному заданию

По отдельному запросу добавлены русский и английский языки, показ/скрытие пароля, иконки Lucide, анимированные скелетоны загрузки, профиль и создание сотрудников постановщиками. Пользовательские названия, адреса и комментарии не переводятся. Выбор языка сохраняется в браузере; анимация отключается при предпочтении уменьшенного движения.

В профиле доступны имя, email, роль, дата регистрации и сводка задач. Пользователь может менять только своё имя. Постановщик дополнительно видит список сотрудников и создаёт аккаунты обеих ролей. Email сотрудников выдаются только через защищённую функцию `list_staff`.

Создание аккаунтов выполняет Supabase Edge Function `create-staff`. Она проверяет токен через `auth.getUser()` и читает роль из базы на каждом запросе: анонимный запрос получает 401, исполнитель — 403. Проверка токена шлюзом для этой функции отключена, поскольку проверка реализована внутри самой функции. Административный ключ берётся из встроенного серверного окружения Supabase и не передаётся клиенту. Триггер создаёт профиль по защищённым `app_metadata`; редактируемые пользователем `user_metadata` не используются для назначения ролей. Существующие имя и роль при обновлении метаданных не перезаписываются.

## Проверки

```sh
corepack yarn test
corepack yarn test:db
corepack yarn test:api
corepack yarn test:staff
corepack yarn typecheck
corepack yarn lint
corepack yarn build
```

Проверено: **6 тестов интерфейсных правил, переводов и валидации**, **150 проверок базы**, **47 прямых проверок основного API** и **29 проверок профиля и создания сотрудников**. Проверки TypeScript, ESLint и сборка также пройдены. Подробности и границы проверки приведены в [отчёте](docs/verification.md).

Для `test:db` нужны PostgreSQL и команды `initdb`, `pg_ctl`, `psql`; путь можно задать через `PG_BIN`. Проверка создаёт и удаляет отдельную временную базу. Для `test:api` и `test:staff` нужны `.env.admin` и подготовленные демо-доступы. Эти проверки используют временные записи; существующие аккаунты и демо-задачи не меняются. Проверка сотрудников удаляет только созданные ею аккаунты.

## Решения и ограничения

- Удаление мягкое: запись исчезает из приложения, но история сохраняется в базе. Удаление объекта скрывает и его задачи. Восстановления через интерфейс нет.
- Описание задачи необязательно. Редактирование и переназначение сохраняют статус, автора, дату создания и историю; предыдущий исполнитель теряет доступ после переназначения.
- Загружается до 1000 видимых записей на таблицу; для большого набора потребуется постраничная загрузка.
- Нет вложений, уведомлений, автоматического обновления данных, изменения ролей и удаления сотрудников через интерфейс. Пароли для первого входа не истекают автоматически.
- Safari, Firefox, реальные телефоны и нагрузочные испытания не проверялись. Сборка предупреждает об одном крупном файле JavaScript; для тестового приложения разделение загрузки не добавлялось.
- На Supabase Free недоступна проверка паролей по базе утечек. Это отмечено в [отчёте](docs/verification.md); открытая регистрация отключена, демо-пароли случайные.

## Развёртывание и устройство проекта

Фронтенд размещён на Vercel Free, база, авторизация и функция создания сотрудников — на Supabase Free. Отдельный собственный сервер не разворачивается.

При импорте репозитория в Vercel задайте две публичные переменные фронтенда и `ENABLE_EXPERIMENTAL_COREPACK=1`. Используйте Vite, команду `yarn build` и каталог `dist`. Настройка в `vercel.json` обеспечивает открытие вложенных адресов приложения напрямую. Административные переменные Vercel не нужны.

- `src` — авторизация, страницы, формы, переводы и компоненты интерфейса.
- `supabase/migrations` — таблицы, права доступа, транзакционные функции и триггеры.
- `supabase/functions/create-staff` — серверное создание сотрудников.
- `scripts` — подготовка данных и проверки базы/API.
- `docs` — объяснение для руководителя, допущения, результаты проверки и шаблон сообщения для hh.ru.

Конфиги `.mjs`/`.mts` и `src/package.json` с ES-модулями предотвращают конфликт Yarn 4 с окружением Vercel. При изменении схемы синхронизируйте `src/database.types.ts` с базой (`supabase gen types typescript`).
